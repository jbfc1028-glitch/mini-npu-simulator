
# Mini NPU Simulator

## 1. 프로젝트 소개

Python으로 NPU의 기본 연산인 MAC(Multiply-Accumulate)을 구현한 시뮬레이터입니다.

입력 패턴과 두 필터의 MAC 점수를 계산하여 어느 필터와 더 유사한지 판정합니다.

## 2. 개발 환경

- Python 3.8 이상
- 외부 라이브러리 사용하지 않음
- Python 표준 라이브러리 json, time 사용

## 3. 실행 방법

프로젝트 폴더에서 다음 명령어를 실행합니다.

```bash
python main.py
```

실행 후 메뉴를 선택합니다.

- 1번: 3×3 필터와 패턴 직접 입력
- 2번: data.json 자동 테스트
- 3번: MAC 성능 비교
- 0번: 프로그램 종료

`main.py`와 `data.json`은 같은 프로젝트 폴더에 위치해야 합니다.

1번 직접 입력 모드에서는 필터 A, 필터 B, 입력 패턴을 각각 3줄씩 입력하며, MAC 점수와 판정 결과를 확인할 수 있습니다. 이후 성능 분석 결과가 자동으로 출력됩니다.

2번 JSON 테스트 모드에서는 데이터 검증 및 판정을 수행한 후 성능 분석 결과와 전체 테스트 요약을 출력합니다.

3번 메뉴를 선택하면 성능 분석만 별도로 실행할 수도 있습니다.

## 4. 주요 기능

### MAC 연산

입력 패턴과 필터의 같은 위치에 있는 숫자를 곱하고 모두 더합니다.

MAC = Σ(입력값 × 필터값)

이중 for 반복문을 사용하여 구현했습니다.

### MAC 점수의 의미와 해석

MAC 점수는 입력 패턴과 필터의 같은 위치에 있는 원소를 곱한 뒤 모두 더한 값입니다.

현재 프로그램에서는 두 필터의 MAC 점수를 비교하여 더 높은 점수를 얻은 필터를 판정 결과로 선택합니다.

예를 들어 Cross 점수가 8.9이고 X 점수가 0.1이라면 Cross 필터의 점수가 더 높으므로 `Cross`로 판정합니다.

MAC 점수가 높다는 것은 해당 필터와 입력 패턴의 곱셈 누적 결과가 크다는 의미입니다.

다만 MAC 점수는 정규화된 유사도 점수가 아니므로, 점수의 절댓값만으로 패턴의 유사도를 정확하게 판단할 수는 없습니다.

입력값과 필터값의 크기 및 부호도 점수에 영향을 주기 때문에, 현재 프로그램에서는 두 필터의 상대적인 점수 차이를 기준으로 판정합니다.

### calculate_mac() 함수의 입력과 출력

MAC 연산은 `calculate_mac(pattern, filter_data)` 함수에서 수행합니다.

**함수 구조**

```python
def calculate_mac(pattern, filter_data):
    score = 0.0
    for i in range(len(pattern)):
        for j in range(len(pattern[i])):
            score += pattern[i][j] * filter_data[i][j]
    return score
```

**매개변수 및 반환값**

- `pattern`: MAC 연산에 사용할 입력 패턴으로, 숫자로 구성된 2차원 리스트입니다.
- `filter_data`: 입력 패턴과 곱할 필터로, 숫자로 구성된 2차원 리스트입니다.
- `score`: 같은 위치의 원소끼리 곱한 결과를 모두 더한 점수입니다.
- `return score`: 최종 MAC 점수를 반환합니다.

**데이터 처리 흐름**

`입력 패턴 + 필터 → 같은 위치의 원소끼리 곱셈 → 결과 누적 → MAC 점수 반환`

예를 들어 다음과 같이 함수를 호출할 수 있습니다.

```python
pattern = [[1, 0], [0, 1]]
filter_data = [[1, 0], [0, 1]]

result = calculate_mac(pattern, filter_data)
print(result)
```

실행 결과:

```text
2.0
```

이 예시에서는 `1×1 + 0×0 + 0×0 + 1×1 = 2.0`이 계산됩니다.

이 함수는 점수를 계산하여 반환하는 역할만 담당하며, 최종 패턴 판정은 별도의 `judge_pattern()` 함수에서 수행합니다.

### 판정 방식

두 필터의 MAC 점수를 비교합니다.

- Cross 점수가 높으면 Cross
- X 점수가 높으면 X
- 점수 차이가 1e-9보다 작으면 UNDECIDED

직접 입력 모드에서는 Cross와 X 대신 A와 B로 출력합니다.

### epsilon(허용오차) 설정 이유

Python의 실수(float)는 부동소수점 방식으로 저장되기 때문에 계산 과정에서 미세한 오차가 발생할 수 있습니다.

예를 들어 수학적으로 같은 점수라도 실제 계산 결과는 `0.9`와 `0.8999999999999999`처럼 다르게 나타날 수 있습니다.

이러한 차이를 동점으로 처리하기 위해 epsilon을 `1e-9`(0.000000001)로 설정했습니다.

epsilon은 별도의 시간 단위가 아니라 MAC 점수 차이에 적용하는 허용오차이므로 MAC 점수와 같은 단위를 가집니다. 현재 프로그램의 MAC 점수에는 별도의 물리적 단위가 없습니다.

epsilon을 더 작게 설정하면 미세한 차이도 승패로 구분할 수 있고, 더 크게 설정하면 더 많은 경우가 `UNDECIDED`로 처리됩니다.

### epsilon(1e-9) 숫자 표기법과 동점 판정 예시

Python에서 `e`는 10의 거듭제곱을 나타내는 지수 표기법입니다.

예를 들어 `1e-9`는 1이 아니라 `1 × 10⁻⁹`를 의미하며, 실제 숫자로 표현하면 `0.000000001`입니다.

| Python 표현 | 실제 숫자 | 의미 |
|---|---:|---|
| `1e0` | 1 | 1 |
| `1e1` | 10 | 10의 1제곱 |
| `1e2` | 100 | 10의 2제곱 |
| `1e-1` | 0.1 | 10분의 1 |
| `1e-3` | 0.001 | 1,000분의 1 |
| `1e-9` | 0.000000001 | 10억분의 1 |

양수 지수는 숫자가 커지는 방향이고, 음수 지수는 숫자가 작아지는 방향입니다.

현재 프로그램에서는 다음과 같이 사용합니다.

```python
epsilon = 1e-9

if abs(score_cross - score_x) < epsilon:
    return "UNDECIDED"
```

여기서 `abs()`는 두 점수 차이의 절댓값을 구하는 함수입니다.

즉, 두 점수의 차이가 `0.000000001`보다 작으면 사실상 동점으로 판단합니다.

**실제 판정 예시**

| Cross 점수 | X 점수 | 판정 결과 | 이유 |
|---|---|---|---|
| 0.9 | 0.8999999999999999 | UNDECIDED | 점수 차이가 epsilon보다 작음 |
| 0.9 | 0.8 | Cross | Cross 점수가 더 높음 |
| 0.5 | 0.7 | X | X 점수가 더 높음 |
| 1.0 | 1.0 | UNDECIDED | 두 점수가 정확히 같음 |

**핵심 정리**

- `1e-9`는 `0.000000001`을 의미합니다.
- epsilon은 부동소수점 계산에서 발생하는 미세한 오차를 허용하기 위한 기준입니다.
- 점수 차이가 epsilon보다 작으면 `UNDECIDED`로 판정합니다.
- 점수 차이가 epsilon 이상이면 더 높은 점수를 가진 필터를 선택합니다.

### 직접 입력 모드 출력 예시

직접 입력 모드에서는 필터 A와 필터 B의 MAC 점수, 판정 결과, 연산 시간을 출력합니다.

아래는 출력 예시입니다.

```text
=== MAC 연산 결과 ===
A 점수: 5.0
B 점수: 1.0
연산 시간: 0.005000 ms
판정 결과: A
```

연산 시간은 실행 환경에 따라 달라질 수 있습니다.

### 모드별 동점 처리 방식

직접 입력 모드와 JSON 테스트 모드는 동일한 epsilon(1e-9) 기준을 사용합니다.

두 필터의 MAC 점수 차이의 절댓값이 1e-9보다 작으면 두 모드 모두 `UNDECIDED`로 판정합니다.

직접 입력 모드에서는 필터를 A와 B로 구분하며, 판정 결과를 `A`, `B`, `UNDECIDED` 중 하나로 출력합니다. 별도의 기대 정답이 없으므로 PASS/FAIL은 계산하지 않습니다.

JSON 테스트 모드에서는 필터를 Cross와 X로 구분하며, 판정 결과를 `Cross`, `X`, `UNDECIDED` 중 하나로 출력합니다. 이 결과를 JSON의 기대 정답과 비교하여 PASS 또는 FAIL을 결정합니다.

예를 들어 `size_5_1`은 두 점수가 약 0.9로 사실상 같아 `UNDECIDED`로 판정되지만, 기대 정답이 `X`이므로 FAIL로 처리됩니다.

따라서 두 모드의 동점 판정 기준은 동일하며, 출력 라벨과 기대 정답 비교 여부에 차이가 있습니다.

### 동점 판정 시 점수 차이 출력

두 필터의 MAC 점수 차이가 epsilon(1e-9)보다 작아 `UNDECIDED`로 판정되면, 두 점수의 차이를 추가로 출력합니다.

점수 차이는 `abs(score_cross - score_x)`로 계산하며, 직접 입력 모드에서는 필터 A와 B의 점수 차이를 계산합니다.

**JSON 테스트 모드 출력 예시**

```text
테스트: size_5_1
Cross 점수: 0.9000
X 점수: 0.9000
동점 판정 - 점수 차이: 1.11022302463e-16
판정 결과: UNDECIDED
기대 정답: X
테스트 결과: FAIL
```

이를 통해 소수점 넷째 자리까지 출력된 점수가 같아 보이더라도 실제 계산에서는 미세한 차이가 존재한다는 사실을 확인할 수 있습니다.

점수 차이는 판정 이유를 설명하기 위한 추가 정보이며, 기존 epsilon 기준이나 PASS/FAIL 결과를 변경하지 않습니다.

### JSON 테스트

data.json에서 필터와 입력 패턴을 불러옵니다.

패턴 크기에 맞는 필터를 선택하고 MAC 점수를 계산합니다.

기대 정답과 비교하여 PASS 또는 FAIL을 출력합니다.

### JSON 테스트 키 이름 규칙

JSON 테스트 데이터는 정해진 키 이름 형식을 사용합니다.

**필터 키 형식**

`size_N`

여기서 `N`은 행렬의 한 변의 크기를 의미합니다.

예시:
- `size_5`: 5×5 필터
- `size_13`: 13×13 필터
- `size_25`: 25×25 필터

**패턴 테스트 ID 형식**

`size_N_번호`

여기서 `N`은 행렬 크기이며, `번호`는 해당 크기의 테스트를 구분하는 식별자입니다.

예시:
- `size_5_1`: 5×5 첫 번째 테스트
- `size_5_2`: 5×5 두 번째 테스트
- `size_13_1`: 13×13 첫 번째 테스트

프로그램은 테스트 ID에서 마지막 `_번호`를 제거하여 필터 키를 찾습니다.

예를 들어 `size_5_1`에서 `size_5`를 추출한 뒤, 해당 필터를 사용하여 MAC 점수를 계산합니다.

**잘못된 키 이름 처리**

테스트 ID가 규칙과 다르거나 해당 크기의 필터가 존재하지 않으면 테스트 실행 중 오류가 발생할 수 있습니다.

현재 프로그램은 `KeyError`, `ValueError`, `TypeError`, `IndexError`를 처리하여 해당 테스트를 FAIL로 기록하고 다음 테스트를 계속 진행합니다.

따라서 JSON 데이터를 작성할 때는 필터 키와 테스트 ID의 크기가 서로 일치하도록 작성해야 합니다.

### 성능 비교

3×3, 5×5, 13×13, 25×25 크기의 행렬을 각각 100회 연산합니다.

각 크기별 MAC 연산 횟수와 평균 실행 시간을 밀리초(ms) 단위로 출력합니다.

성능 측정은 최소 10회 이상 반복한다는 요구사항에 따라 각 행렬 크기별로 100회 수행합니다. 평균 실행 시간은 전체 측정 시간을 반복 횟수로 나누어 계산하며, 100회 반복을 통해 단일 측정에서 발생할 수 있는 시간 변동의 영향을 줄였습니다.

### 입력값 및 JSON 오류 검증

직접 입력 모드에서는 각 행에 숫자 3개를 입력했는지 확인합니다.

숫자의 개수가 잘못되거나 문자 등 숫자로 변환할 수 없는 값이 입력되면 오류 메시지를 출력하고 해당 행을 다시 입력받습니다.

JSON 테스트 모드에서는 필수 키의 존재 여부와 데이터 구조를 확인합니다.

각 패턴과 필터의 행렬 크기 및 숫자 형식을 검증하며, 잘못된 데이터가 발견되면 해당 테스트를 FAIL로 처리합니다.

이때 프로그램 전체가 종료되지 않고 나머지 테스트를 계속 수행하도록 구현했습니다.

실제 검증 과정에서 숫자 대신 문자열이 입력된 경우와 5×5 행렬이 4×5로 변경된 경우 모두 오류를 감지하는 것을 확인했습니다.

### JSON 파일 로드 오류 및 복구 방법

JSON 테스트 모드는 현재 작업 폴더에 있는 `data.json` 파일을 불러옵니다.

파일이 존재하지 않으면 `FileNotFoundError`를 처리하여 다음 메시지를 출력합니다.

```text
오류: data.json 파일을 찾을 수 없습니다.
```

JSON 문법이 잘못된 경우에는 `JSONDecodeError`를 처리하여 다음 메시지를 출력합니다.

```text
오류: JSON 파일 형식이 올바르지 않습니다.
```

파일을 불러오지 못하면 JSON 테스트를 실행하지 않고 메인 메뉴로 돌아갑니다.

이 경우 다음 사항을 확인한 뒤 메뉴에서 2번을 다시 선택하면 됩니다.

1. 파일 이름이 정확히 `data.json`인지 확인합니다.
2. 터미널의 현재 작업 폴더가 프로젝트 폴더인지 확인합니다.
3. `data.json` 파일이 해당 폴더에 존재하는지 확인합니다.
4. JSON 문법 오류가 있다면 수정한 뒤 다시 실행합니다.

현재 프로그램은 다른 파일 경로를 자동으로 검색하거나 재시도하지 않습니다. 사용자가 파일 위치 또는 실행 경로를 수정한 뒤 다시 시도하는 방식입니다.

### 직접 입력 모드의 재입력 및 종료 방법

직접 입력 모드에서는 각 행에 숫자 3개를 입력해야 합니다.

입력한 숫자의 개수가 3개가 아니거나 숫자로 변환할 수 없는 값이 포함되면 오류 메시지를 출력하고 같은 행을 다시 입력받습니다.

정상적인 행 3개를 입력하면 다음 행렬 입력 단계로 넘어가며, 필터 A, 필터 B, 패턴의 입력이 모두 완료되면 MAC 연산을 수행합니다.

입력 도중 실행을 중단하려면 터미널에서 `Ctrl + C`를 누를 수 있습니다. 이 경우 프로그램 전체가 종료되며 메인 메뉴로 돌아가지는 않습니다.

정상적으로 입력을 완료한 뒤에는 메인 메뉴에서 `0`을 선택하여 프로그램을 종료할 수 있습니다.

## 5. 결과 리포트

### 5.1 JSON 테스트 결과

제공된 data.json을 기준으로 총 6개의 패턴을 분석했습니다.

| 테스트 ID | Cross 점수 | X 점수 | 판정 | 기대 정답 | 결과 |
|---|---:|---:|---|---|---|
| size_5_1 | 0.9000 | 0.9000 | UNDECIDED | X | FAIL |
| size_5_2 | 8.9000 | 0.1000 | Cross | Cross | PASS |

실패 비율은 `(FAIL 개수 / 전체 테스트 개수) × 100`으로 계산합니다. 전체 테스트가 0개인 경우에는 0으로 처리하여 나눗셈 오류를 방지합니다.

### JSON 테스트 콘솔 출력 예시

아래는 `data.json`의 `size_5_1` 테스트를 실행했을 때의 실제 출력 예시입니다.

```text
테스트: size_5_1
Cross 점수: 0.9000
X 점수: 0.9000
동점 판정 - 점수 차이: 1.11022302463e-16
판정 결과: UNDECIDED
기대 정답: X
테스트 결과: FAIL
```

이 테스트에서는 두 MAC 점수의 차이가 epsilon(1e-9)보다 작으므로 `UNDECIDED`로 판정됩니다.

하지만 JSON에 저장된 기대 정답은 `X`이므로 최종 테스트 결과는 `FAIL`입니다.

### 5.2 라벨 정규화

JSON 파일의 필터 키와 기대 정답은 서로 다른 표기법을 사용합니다.

- 필터 키 cross → Cross
- 필터 키 x → X
- 기대 정답 + → Cross
- 기대 정답 x → X

프로그램에서는 Cross와 X를 표준 라벨로 사용합니다.
이를 통해 서로 다른 표기로 인해 판정 비교가 잘못되는 문제를 방지합니다.

라벨 정규화는 `normalize_label(label)` 함수로 분리하여 구현했습니다.

이 함수는 `+`, `cross`, `Cross`를 `Cross`로 변환하고, `x`, `X`를 `X`로 변환합니다. 지원하지 않는 라벨은 `ValueError`를 발생시킵니다.

필터 키와 기대 정답 모두 동일한 함수를 사용하므로 중복 코드를 줄이고 재사용성을 높였습니다. 또한 정규화 기능을 독립적으로 테스트할 수 있어 유지보수가 편리합니다.

### 라벨 정규화 처리 흐름

JSON 데이터의 필터 키와 기대 정답은 `normalize_label()` 함수를 통해 표준 라벨로 변환됩니다.

**처리 흐름**

`JSON 라벨 입력 → normalize_label() 호출 → 표준 라벨 변환 → MAC 판정 결과와 비교`

**라벨 변환 예시**

| JSON 입력 라벨 | 표준 라벨 |
|---|---|
| `+` | `Cross` |
| `cross` | `Cross` |
| `Cross` | `Cross` |
| `x` | `X` |
| `X` | `X` |

예를 들어 JSON의 기대 정답이 `"+"`라면 `normalize_label("+")`를 호출하여 `"Cross"`로 변환합니다.

필터 키도 같은 함수를 사용하여 정규화한 뒤 해당 필터로 MAC 점수를 계산합니다.

지원하지 않는 라벨이 입력되면 `ValueError`가 발생하며, JSON 테스트에서는 해당 케이스를 FAIL로 처리합니다.

### 라벨 확장 및 테스트 절차

현재 프로그램은 `Cross`와 `X` 두 가지 라벨을 지원합니다.

향후 새로운 라벨을 추가할 경우 다음 절차에 따라 기능을 확장할 수 있습니다.

1. `normalize_label()` 함수에 새로운 라벨과 허용할 입력 표기법을 추가합니다.
2. `data.json`의 필터와 기대 정답에 새로운 라벨을 반영합니다.
3. `run_json_tests()`에서 새로운 필터를 읽고 MAC 점수를 계산할 수 있도록 수정합니다.
4. `judge_pattern()`의 판정 로직을 확장하여 새로운 라벨도 비교할 수 있도록 변경합니다.
5. 새로운 라벨이 포함된 정상 데이터를 실행하여 PASS/FAIL 결과가 올바른지 확인합니다.
6. 잘못된 라벨, 누락된 필터, 잘못된 행렬 크기를 입력하여 오류 처리 기능을 검증합니다.
7. 기존 Cross/X 테스트 6개를 다시 실행하여 기존 기능에 문제가 없는지 확인합니다.

새로운 라벨을 추가할 때는 정규화 함수뿐 아니라 필터 처리와 판정 로직도 함께 수정해야 합니다.

이를 통해 새로운 기능을 추가하더라도 기존 기능이 정상적으로 유지되는지 검증할 수 있습니다.

### 5.3 실패 원인 분석

1. 총 6개 테스트 중 3개가 PASS, 3개가 FAIL로 판정되었습니다.
2. size_5_1의 Cross 점수와 X 점수는 모두 약 0.9입니다.
3. 두 점수의 차이가 epsilon보다 작아 UNDECIDED로 판정됩니다.
4. 그러나 기대 정답은 X이므로 FAIL이 발생합니다.
5. size_13_2의 두 점수는 모두 약 7.5입니다.
6. 이 경우에도 동점 처리 정책에 따라 UNDECIDED가 출력됩니다.
7. 기대 정답은 Cross이므로 FAIL로 처리됩니다.
8. size_25_1의 두 점수는 모두 약 4.9입니다.
9. 기대 정답은 X이지만 UNDECIDED가 출력되어 FAIL이 발생합니다.
10. Python의 부동소수점 계산에서는 미세한 수치 오차가 발생할 수 있습니다.
11. 이를 해결하기 위해 abs(score_a - score_b) < 1e-9를 동점 기준으로 사용했습니다.
12. 데이터 및 스키마 문제는 행렬 크기, 숫자 형식, 필수 키를 검증하여 구분합니다.
13. 로직 문제는 MAC 계산 결과와 판정 조건이 올바른지 확인하여 진단할 수 있습니다.
14. 수치 비교 문제는 부동소수점 오차와 epsilon 정책을 확인하여 분석합니다.
15. 이번 3개의 FAIL은 주로 두 필터의 점수가 사실상 동일한 수치 비교 문제에서 발생했습니다.
16. 실제 오류 데이터를 사용한 테스트에서는 숫자 대신 문자열이 들어간 패턴을 FAIL로 처리하는 것도 확인했습니다.
17. 따라서 모든 FAIL이 프로그램 오류를 의미하지는 않으며, 필터의 구분 능력과 비교 정책을 함께 검토해야 합니다.

### 5.4 성능 분석 결과

각 크기별 MAC 연산을 100회 반복하여 평균 시간을 측정했습니다.

|---|---:|---:|
| 3×3 | 0.000815 | 9 |
| 5×5 | 0.001528 | 25 |
| 13×13 | 0.008217 | 169 |
| 25×25 | 0.022761 | 625 |

측정에는 time.perf_counter()를 사용했습니다.
입출력과 파일 읽기 시간을 제외하고 MAC 연산 함수의 실행 시간을 측정했습니다.

측정 시간은 컴퓨터의 성능과 실행 환경에 따라 달라질 수 있습니다.

### 성능 측정의 워밍업(Warm-up)과 정확도

현재 프로그램은 `time.perf_counter()`를 사용하여 MAC 연산을 100회 반복 실행하고, 전체 소요 시간을 반복 횟수로 나누어 평균 실행 시간을 계산합니다.

다만 현재 구현에는 별도의 워밍업 과정이 포함되어 있지 않습니다.

워밍업은 실제 성능 측정 전에 MAC 연산을 여러 번 실행하여 초기 실행 환경과 캐시 상태 등의 영향을 줄이기 위한 방법입니다.

향후 측정 정확도를 개선할 때는 본 측정 전에 MAC 연산을 일정 횟수 실행하고, 워밍업에 소요된 시간은 평균 계산에서 제외할 수 있습니다.

또한 측정 결과는 CPU 상태, 운영체제의 작업 스케줄링, 캐시 상태 등에 따라 달라질 수 있으므로 여러 번 측정하여 비교하는 것이 좋습니다.

### 5.5 시간 복잡도 분석

MAC 연산은 N×N 행렬의 모든 위치를 순회합니다.

첫 번째 for 반복문은 N번 실행되고,
두 번째 for 반복문도 각 행마다 N번 실행됩니다.

따라서 총 N×N = N²개의 원소에 대해 곱셈과 누적 덧셈을 수행합니다.

시간 복잡도는 O(N²)입니다.

실제 측정에서도 행렬 크기가 커질수록 평균 연산 시간이 증가했습니다.

3×3 행렬에서는 9번의 MAC 연산이 필요하지만,
25×25 행렬에서는 625번의 MAC 연산이 필요합니다.

이는 행렬의 한 변의 크기가 증가할수록
전체 연산량이 제곱에 비례하여 증가한다는 것을 보여줍니다.

### 행렬 크기 증가에 따른 실행 시간 비교

행렬의 한 변의 크기 N이 증가하면 MAC 연산 횟수는 N²에 비례하여 증가합니다.

실제 성능 측정 결과에서도 행렬 크기가 커질수록 평균 실행 시간이 증가하는 경향을 확인했습니다.

| 비교 항목 | 3×3 | 25×25 |
|---|---:|---:|
| MAC 연산 횟수 | 9 | 625 |
| 평균 실행 시간(ms) | 0.000815 | 0.022761 |

3×3과 25×25를 비교하면 MAC 연산 횟수는 약 69.4배 증가했고, 평균 실행 시간은 약 27.9배 증가했습니다.

두 증가 비율이 정확히 일치하지 않는 이유는 Python 반복문 실행 비용, 함수 호출 비용, CPU 상태 및 측정 오차 등이 영향을 주기 때문입니다.

따라서 실제 측정값이 연산 횟수와 완전히 같은 비율로 증가하지 않더라도, 이중 반복문으로 모든 원소를 처리하는 알고리즘의 시간 복잡도는 O(N²)입니다.

이 결과는 입력 행렬이 커질수록 처리해야 하는 연산량이 증가하고, 실행 시간도 전반적으로 증가한다는 사실을 보여줍니다.

### 5.6 대규모 패턴 처리 및 최적화 방향

현재 MAC 연산은 이중 `for`문을 사용하여 N×N 행렬의 모든 원소를 순차적으로 계산합니다.

따라서 행렬 크기가 증가하면 연산 횟수가 N²에 비례하여 증가하며, 실행 시간도 길어질 수 있습니다.

예를 들어 25×25 행렬은 625개의 원소를 처리하지만, 1000×1000 행렬은 1,000,000개의 원소를 처리해야 합니다.

메모리 측면에서는 입력 패턴과 필터를 2차원 리스트로 저장하므로 각 행렬에 O(N²)의 저장 공간이 필요합니다.

현재 `calculate_mac()` 함수 자체는 누적 점수와 반복문 변수만 사용하므로 추가 작업 공간은 O(1)입니다.

대규모 입력에서 예상되는 주요 병목은 Python의 반복문 실행 비용과 많은 행렬 원소에 접근하는 과정입니다.

우선적인 최적화 방향은 반복문 내부의 불필요한 연산을 줄이고, 데이터 접근 방식을 개선하는 것입니다.

추가로 입력 데이터를 한 번에 모두 복사하지 않고 필요한 부분만 처리하는 방식도 검토할 수 있습니다.

더 큰 성능 개선이 필요한 경우에는 병렬 처리나 벡터화 연산을 고려할 수 있습니다. 다만 현재 과제는 Python 표준 라이브러리만 사용하므로 외부 수치 연산 라이브러리는 적용하지 않았습니다.

최적화 전후에는 동일한 입력 데이터로 반복 측정을 수행하여 실행 시간과 메모리 사용량을 비교해야 합니다.

### 5.7 CPU와 NPU의 연산 방식 비교

현재 Mini NPU Simulator는 Python의 이중 `for`문을 이용하여 MAC 연산을 순차적으로 수행하는 CPU 기반 시뮬레이터입니다.

실제 NPU(Neural Processing Unit)는 신경망 연산에 특화된 하드웨어로, 여러 곱셈과 누적 연산을 병렬로 처리할 수 있도록 설계되어 있습니다.

현재 프로그램은 행렬의 각 원소를 하나씩 순회하므로 행렬 크기가 증가할수록 반복문 실행 시간이 길어지는 문제가 있습니다.

반면 NPU는 다수의 연산 장치를 활용하여 여러 MAC 연산을 동시에 수행할 수 있어 대규모 행렬 연산에서 높은 처리량을 기대할 수 있습니다.

하지만 NPU에서도 모든 연산이 무조건 빠르게 실행되는 것은 아닙니다.

연산에 필요한 데이터를 메모리에서 가져오는 속도가 충분하지 않으면 메모리 대역폭이 병목이 될 수 있습니다.

또한 여러 연산 장치가 작업 결과를 합치거나 실행 순서를 맞추는 과정에서 동기화 비용이 발생할 수 있습니다.

CPU 기반 구현에서는 Python 반복문 실행 비용과 데이터 접근 비용이 주요 병목이며, NPU에서는 병렬 연산 장치의 활용률, 메모리 대역폭, 데이터 이동 및 동기화 비용 등이 성능에 영향을 줍니다.

따라서 NPU의 성능을 높이려면 단순히 연산 장치를 늘리는 것뿐 아니라 데이터 재사용과 메모리 접근을 효율적으로 설계하는 것이 중요합니다.

본 프로젝트는 실제 NPU 하드웨어의 병렬 실행을 구현한 것이 아니라, NPU의 핵심 연산인 MAC과 패턴 판정 원리를 Python으로 학습하기 위한 시뮬레이터입니다.
